======================================================================
PROJECT PROBLEM STATEMENT
======================================================================

Project:
Intelligent Data Capture & Schedule-Linking Layer for Infrastructure
Project Management.

The system connects:
- structured project schedules
- unstructured field progress
- AI extraction
- schedule matching
- confidence evaluation
- planner review
- audit trail

The problem statement emphasizes an LLM-based conversational interface
for site supervisors and a "minimal friction" / "low-friction" mechanism
for logging field activity.

WhatsApp is being added as the practical field communication channel.

The important design principle is:

WhatsApp is ONLY AN INPUT CHANNEL.

It must reuse the existing ConSight intelligence pipeline rather than
creating a second AI system.

======================================================================
PHASE 5 OBJECTIVE
======================================================================

Allow a site supervisor to send a WhatsApp text message containing
field progress.

Example:

"XX-101 ka spool erection 9:30 baje start kiya"

or:

"Today at 9:30 AM, the piping team started erection of the XX-101
spool in Area B."

The system should:

WhatsApp message
      |
      v
WhatsApp webhook
      |
      v
ConSight backend
      |
      v
Existing extraction service
      |
      v
Structured Progress Event
      |
      v
Existing Phase 2 matching
      |
      v
Existing Phase 3 confidence/review workflow
      |
      v
Stored result + response
      |
      v
WhatsApp reply

The goal is to prove that supervisors can submit field progress without
learning a new application.

======================================================================
WHATSAPP INTEGRATION
======================================================================

Implement a WhatsApp Business Cloud API webhook using the existing
FastAPI backend.

The implementation should support:

1. Webhook verification
2. Incoming message handling
3. Text-message extraction
4. Sender/session identification
5. Routing message into the existing ConSight agent flow
6. Sending a response back through WhatsApp
7. Safe error handling
8. Testable provider abstraction

Do NOT hard-code WhatsApp credentials.

Use environment variables.

======================================================================
WEBHOOK DESIGN
======================================================================

Implement a dedicated WhatsApp route, for example:

GET  /whatsapp/webhook
POST /whatsapp/webhook

Adapt the exact route naming to the existing API conventions.

GET should support WhatsApp webhook verification.

POST should:
- validate the webhook request
- identify the incoming message
- ignore unsupported/non-text events safely
- identify sender
- create/reuse an appropriate session identifier
- pass the message to the existing agent service
- generate the ConSight response
- send the response using the WhatsApp provider abstraction
- return an appropriate HTTP response quickly

Keep route handlers thin.

======================================================================

======================================================================

Implement the standard WhatsApp Cloud API webhook verification flow.

Use environment variables for:
- verify token
- access token
- phone number ID
- API configuration

Do NOT hard-code credentials.

Verification failures must return appropriate errors.

Never expose secrets in logs or API responses.

======================================================================
WHATSAPP PROVIDER ABSTRACTION
======================================================================

Create a clean provider/service abstraction.

Conceptually:

WhatsAppProvider
    |
    +-- verify_webhook()
    |
    +-- parse_incoming_message()
    |
    +-- send_text_message()

The exact class/function design should follow the existing project style.

The core ConSight business logic must NOT depend directly on raw
WhatsApp API payload structures.

This makes the integration testable and replaceable.

======================================================================
INCOMING MESSAGE HANDLING
======================================================================

Handle normal WhatsApp text messages.

Extract only the information actually provided by WhatsApp, such as:
- sender identifier
- message identifier
- timestamp
- text body
- phone number metadata when legitimately available

Do NOT infer:
- activity ID
- discipline
- location
- dates
- equipment tag
- actual progress
- identity beyond the data supplied by the webhook

The existing AI extraction service should determine structured
progress fields from the message.

Maintain the project's no-hallucination rule.

======================================================================
SESSION HANDLING
======================================================================

The same supervisor should be able to have a conversational interaction
through WhatsApp.

Reuse the existing agent session mechanism if available.

Use the WhatsApp sender identifier as the basis for mapping a WhatsApp
conversation to an agent session where appropriate.

Do NOT introduce a complicated authentication/user-management system.

For the SIH MVP, a simple deterministic session mapping is sufficient.

If persistent mapping is required, implement the smallest database
change necessary.

Document the design.

======================================================================
RESPONSE FLOW
======================================================================

After receiving a message:

1. Parse incoming WhatsApp message.
2. Pass text to existing agent service.
3. Reuse existing extraction.
4. Reuse existing matching.
5. Reuse existing confidence logic.
6. Reuse existing planner-review behavior.
7. Store relevant events/results using existing persistence.
8. Generate a concise conversational response.
9. Send response back to WhatsApp.

Example successful response:

"Progress recorded for XX-101 spool erection.
Match confidence: 94%.
Status: START logged."

Example ambiguous response:

"I found multiple possible schedule activities.
Please review the suggested matches in ConSight."

Do not claim a match is final when Phase 3 has classified it as requiring
review.

======================================================================
PHASE 3 INTEGRATION
======================================================================

The flow remains:

      |

communicate that the event requires review rather than falsely reporting
that it has been finalized.

DUPLICATE MESSAGE / IDEMPOTENCY
======================================================================

Avoid processing the same incoming message multiple times.

Use the WhatsApp message ID where available.

Implement a simple idempotency mechanism compatible with the existing
database architecture.

Do NOT create an elaborate distributed event-processing system.

A lightweight database-backed approach is enough for the SIH MVP.

Test duplicate delivery.
