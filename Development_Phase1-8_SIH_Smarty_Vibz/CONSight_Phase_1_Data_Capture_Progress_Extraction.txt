SMARTY_VIBZ
PHASE 1 DEVELOPMENT DOCUMENT (UPDATED)
FastAPI Backend Foundation, Intelligent Progress Data Extraction, Multi-Format Ingestion & Conversational Time Agent

1. Phase 1 Objective
Build a working FastAPI backend that accepts an infrastructure project schedule in Excel format, validates and stores schedule activities, accepts messy/free-text field progress reports AND discipline-wise Excel progress reports, uses AI to extract structured progress information, validates that output with Pydantic, stores progress events in SQLite, provides a conversational Time Agent interface for site supervisors, exposes clean APIs, and supports automated tests without depending on a live AI API.

2. Phase 1 Flow
SCHEDULE SIDE: Schedule Excel → Excel Validation → Schedule Activities → SQLite Database

PROGRESS SIDE (FREE TEXT): Field Progress Report → AI Extraction → Pydantic Validation → Structured Progress Event → SQLite Database

PROGRESS SIDE (EXCEL): Discipline-wise Excel → Column Mapping → Row-level Extraction → Pydantic Validation → Structured Progress Event → SQLite Database

TIME AGENT SIDE: Supervisor Chat Input → AI Extraction (reused) → Structured Event → Matching (Phase 2) → Conversational Response

3. Why Phase 1 Matters
The overall project has a structured planning side (L5/L6 schedule) and an unstructured execution side (daily site reports). Phase 1 builds the foundation by answering: "What happened on site?" Phase 2 will later answer: "Which planned activity did that site event belong to?"

The Time Agent directly addresses the problem statement's requirement for "an LLM-based conversational interface for site supervisors across disciplines to log activity start/end with minimal friction."

Example report: "Today at 9:30 AM, the piping team started erection of the XX-101 spool in Area B."
Expected structured event: activity_reference=XX-101 spool erection; event_type=START; event_date=2026-08-30; event_time=09:30; discipline=Piping; location=Area B; equipment_tag=XX-101.

7. Schedule Excel Ingestion

Required columns: activity_code, activity_name, discipline, wbs, planned_start, planned_finish.
7.1 Validation Workflow
Check file type and accept .xlsx.
Check required columns.

Validate individual rows and report malformed rows.
Insert valid rows.
Return total, inserted, failed rows and clear row-level errors.
Never silently ignore bad data.

8. Schedule APIs
POST /schedule/upload — upload and validate schedule Excel.
GET /schedule/activities — view stored schedule activities.

9. AI Progress Extraction
Endpoint: POST /progress/extract
The API receives a free-text report and sends it to the extraction service.
The MVP supports event types: START, PROGRESS, COMPLETE, DELAY, HOLD.
The AI must extract only information supported by the input. Missing fields should be null rather than guessed. Do not hallucinate activity IDs, tags, dates, times, locations, or disciplines.

10. Discipline-wise Excel Progress Upload (NEW)
Endpoint: POST /progress/upload-excel
This endpoint ingests a discipline-wise progress spreadsheet — a different input format from the schedule Excel. This directly satisfies the problem statement's requirement for "2-3 varied input formats."

10.1 Expected Excel Structure
The discipline-wise progress Excel may contain columns such as:
| Column | Description |
|---|---|
| date | Date of the progress report |
| discipline | Civil/Piping/Mechanical/Electrical |
| activity_description | Free-text description of work done |
| status | Started/InProgress/Completed/Delayed/On Hold |
| equipment_tag | Equipment or line tag if available |
| location | Area or location if available |
| reported_by | Name or role of the reporter |

10.2 Processing Workflow
1. Accept .xlsx file upload.
2. Validate required columns (date, activity_description, status).
3. For each row, map the status to the event_type vocabulary:
   - Started → START
   - In Progress → PROGRESS
   - Completed → COMPLETE
   - Delayed → DELAY
   - On Hold → HOLD
4. Combine available columns into a structured progress event.
5. If equipment_tag or location is present in the Excel, use it directly — do not require AI extraction for those fields.
6. If activity_description contains free-text details, optionally run the AI extraction service on it to extract additional structured fields (activity_reference, equipment_tag if missing).
7. Validate each event with Pydantic.
8. Store valid events in progress_events with source_type=EXCEL.
9. Return summary: total rows, extracted events, failed rows, row-level errors.

10.3 Validation Rules
- Missing date → row-level error, skip row.
- Missing activity_description → row-level error, skip row.
- Missing status → default to PROGRESS, do not fail.
- Missing equipment_tag → null, do not guess.
- Missing location → null, do not guess.
- Invalid date format → row-level error.
- Empty Excel file → 400 Bad Request.
- Missing required columns → 400 Bad Request with clear message.

10.4 Excel Progress APIs
POST /progress/upload-excel — upload and process discipline-wise Excel progress report.
GET /progress/events — return stored progress events (includes both free-text and Excel sources).

11. Conversational Time Agent (NEW)
Endpoint: POST /agent/chat
This endpoint provides an LLM-based conversational interface for site supervisors to log activity start/end with minimal friction. This directly satisfies the problem statement's requirement for "an LLM-based conversational interface ('time agent') for site supervisors across disciplines."

11.1 Purpose
The Time Agent replaces rigid manual forms with a natural-language conversation. A supervisor types progress in their own words and the system:
1. Extracts structured progress information (reuses the extraction service).
2. Stores the progress event.
3. If Phase 2 matching is available, runs matching and returns the top match with confidence.
4. Returns a conversational response confirming what was understood and what it was matched to.

11.2 Request Format
{
  "message": "Started XX-101 spool erection at 9:30 AM in Area B",
  "session_id": "optional-session-identifier"
}

11.3 Response Format
{
  "understood": {
    "activity_reference": "XX-101 spool erection",
    "event_type": "START",
    "event_date": "2026-08-30",
    "event_time": "09:30",
    "discipline": "Piping",
    "location": "Area B",
    "equipment_tag": "XX-101"
  },
  "progress_event_id": 17,
  "matched_activity": null,
  "confidence": null,
  "reply": "Got it. I've logged: Piping — START — XX-101 spool erection at 09:30 on 2026-08-30 in Area B. Would you like to run matching now?",
  "follow_up": "You can say 'match it' to find the schedule activity, or log another report."
}

If Phase 2 matching is not yet implemented, matched_activity and confidence should be null, and the reply should indicate the event was logged and matching will be available later.

11.4 Multi-turn Conversation Support
The Time Agent should support basic multi-turn context:
- If the supervisor says "match it" after logging, the agent triggers matching for the most recent event.
- If the supervisor says "log another", the agent resets for a new report.
- If the supervisor says "show me what I logged today", the agent returns today's progress events.

11.5 No-Hallucination Rule (Applies to Time Agent)
The Time Agent must NEVER:
- Invent activity IDs, equipment tags, or dates not present in the supervisor's input.
- Auto-confirm a match without showing the confidence score.
- Silently overwrite existing schedule data.
- Guess missing fields — if a field is missing, ask the supervisor: "What discipline was this for?" or "Which area was this in?"

11.6 Agent APIs
POST /agent/chat — send a message and receive a conversational response.
GET /agent/sessions/{session_id}/events — return all progress events logged in a session.
POST /agent/chat — if the message contains "match" or "match it", trigger Phase 2 matching for the most recent event and return the top match in the conversational response.

12. AI Service Architecture
Keep the LLM call outside the FastAPI route: FastAPI Route → Extraction Service → LLM Provider. This makes the provider replaceable and the tests easier.
Raw LLM Output → Pydantic Schema → Valid Structured Event. Invalid output must be rejected rather than stored.

16. Error Handling

| Condition | Handling |
|---|---|
| Empty progress report | 400 Bad Request |
| Empty agent message | 400 Bad Request |
| Unsupported Excel | 400 Bad Request |
| Missing Excel columns | Clear validation message |
| Invalid date | Row-level error |
| Missing API key | Controlled configuration error |
| AI timeout | Controlled service error |
| Invalid AI JSON | Validation error; do not store |
| Database failure | Appropriate server error without sensitive internals |
| Excel progress missing required columns | 400 Bad Request with message |
| Agent extraction failure | Return conversational error, do not crash |
