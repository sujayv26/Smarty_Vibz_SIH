======================================================================
1. PHASE 7 GOAL
======================================================================

Build a Delay Ripple + Critical Path Impact Engine using the schedule
relationships already imported/preserved by the previous integration
phases.

Example:

Activity A
  ↓ FS
Activity B
  ↓ FS
Activity C

If Activity A is delayed by 3 days, calculate which downstream activities
can be affected and identify whether the delay reaches critical-path or
near-critical activities.

The system should answer:

- What activity was delayed?
- By how much?
- Which successors are affected?
- Which paths are impacted?
- Which activities have zero/low float?
- What is the projected effect on downstream dates?
- Is the project completion date affected?
- What assumptions were used?

Do NOT automatically rewrite the official schedule.

======================================================================
6. DELAY CALCULATION
======================================================================

Implement deterministic date arithmetic.

Examples:

Baseline finish: 2026-09-10
Approved actual/forecast finish: 2026-09-13

Delay = +3 calendar days

But the engine must respect the repository's existing calendar/business
day semantics if available.

Do NOT invent a working calendar.

If only calendar-day arithmetic exists, document that limitation.

======================================================================
7. RELATIONSHIP PROPAGATION
======================================================================

Propagation must depend on relationship type.

For FS:
successor start is constrained by predecessor finish + lag.

For SS:
successor start is constrained by predecessor start + lag.

For FF:
successor finish is constrained by predecessor finish + lag.

For SF:
successor finish is constrained by predecessor start + lag.

The exact date constraints must be implemented mathematically and tested.

Do not reduce all relationships to FS.

======================================================================
8. LAG
======================================================================

Lag must be preserved.

Example:

A → FS + 2d → B

If A finish moves from Sep 10 to Sep 13,
B's earliest constrained start shifts accordingly.

Test:
- positive lag
- zero lag
- negative lag if supported
- invalid lag

Never silently treat missing lag as an arbitrary value.

======================================================================
9. CRITICAL PATH
======================================================================

Implement a deterministic critical-path calculation appropriate to the
schedule graph.

At minimum:
- forward pass
- backward pass
- earliest start
- earliest finish
- latest start
- latest finish
- total float

Critical activities should be identified based on the calculated float,
not on an LLM judgment.

Define the exact critical threshold in code/config and document it.

Handle:
- multiple starting activities
- multiple finishing activities
- disconnected components
- activities with missing dates
- cycles
- malformed relationships

Do not assume the graph is always perfect.

======================================================================
10. CYCLE DETECTION
======================================================================

A valid schedule dependency graph should not contain impossible cycles
for the supported CPM calculation.

Detect cycles explicitly.

Example:
A → B → C → A

Return a structured validation/calculation error.

Never recurse indefinitely.

======================================================================
11. FLOAT / NEAR-CRITICAL
======================================================================

Expose:
- critical
- near-critical
- non-critical

Do not invent a universal threshold without justification.

Prefer:
- configurable threshold
- default documented threshold
- explicit float values in responses

Example:
critical: float <= 0
near-critical: 0 < float <= configured threshold

======================================================================
12. PROJECT COMPLETION IMPACT
======================================================================

Calculate whether a delay changes the calculated project completion date.

Distinguish:

1. Activity delay
2. Downstream date impact
3. Critical path impact
4. Project finish impact

A delayed non-critical activity may have zero project completion impact.

Do not report every delay as a project delay.

======================================================================
13. MULTIPLE DELAYS
======================================================================

Support multiple approved delay inputs where practical.

Avoid double-counting propagated delay.

The graph engine should calculate from a coherent baseline and apply
constraints systematically.

Document precedence/combination rules.

======================================================================
14. EXPLANATION LAYER
======================================================================

The authoritative result comes from deterministic calculations.

Optionally use Nemotron to turn the structured result into a planner-
friendly explanation.

Example structured result:

Successor XX-102 shifts by 3 days.
XX-103 remains within float.
Project finish unchanged.
Critical path unaffected.

Nemotron may produce:
- concise explanation
- planner summary
- plain-language reasoning

- delay amount
- dates
- float
- criticality
- project finish

Validate any generated explanation against the structured result.

If model access fails, deterministic results must still work.
