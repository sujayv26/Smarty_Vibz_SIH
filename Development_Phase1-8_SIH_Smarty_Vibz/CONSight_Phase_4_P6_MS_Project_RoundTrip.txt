CONSight / SMARTY_VIBZ
SIH26122 — PHASE 4 IMPLEMENTATION SPECIFICATION
Primavera P6 Schedule Interoperability and Verified Progress Export

======================================================================
PURPOSE
======================================================================

Phase 1, Phase 2, and Phase 3 are already implemented.

Phase 4 connects the existing ConSight field-progress and matching
workflow with a real infrastructure project schedule.

Phase 4 must:

1. Import a Primavera P6 .XER schedule.
2. Convert imported activities into the existing ConSight schedule model.
3. Preserve activity identifiers, dates, WBS, and useful metadata.
4. Preserve predecessor-successor relationships and lag.
5. Reuse the existing Phase 2 matching engine.
6. Reuse the existing Phase 3 confidence, planner-review, and audit flow.
7. Export a new updated schedule containing only trusted approved actuals.
8. Validate invalid schedule data clearly.
9. Add offline tests and preserve all Phase 1-3 behavior.

Phase 4 is an interoperability feature. It does not train or modify an
LLM. Nemotron may be used as a coding assistant, but the actual feature
must be implemented in the existing FastAPI application and database.

======================================================================
P6/XER IMPORT REQUIREMENTS
======================================================================

Create an isolated P6/XER adapter or parser service.

The adapter must:

- Accept a .xer file.
- Detect empty files.
- Detect malformed XER files.
- Identify schedule activities.
- Extract the external activity identifier.
- Extract activity code where available.
- Extract activity name.
- Extract WBS information where available.
- Extract planned start and planned finish.
- Extract discipline/category where available.
- Extract useful external schedule metadata.
- Extract predecessor-successor relationships.
- Extract relationship type.
- Extract lag where available.
- Normalize dates safely.
- Return structured validation errors.
- Never silently discard important invalid records.
- Never invent missing IDs, names, dates, relationships, or metadata.

The parser must not contain FastAPI route logic or matching logic.

Use the simplest dependable parser compatible with the existing Python
environment. Add a dependency only after checking the current project
dependencies and Python version.

======================================================================
NORMALIZED ACTIVITY MODEL
======================================================================

Use the existing ConSight schedule activity model as the canonical model.
Do not create a parallel P6-only schedule system.

Map imported activities deterministically to existing fields such as:

- activity_code
- activity_name
- discipline
- wbs
- planned_start
- planned_finish
- created_at

If the existing model requires additional fields, add only the minimum
safe metadata, such as:

- source_format
- external_schedule_id
- external_activity_id

Existing Excel schedule import must continue to work.
P6 and Excel activities must coexist through the same internal schedule
concept.

External IDs must remain traceable after import and export.

======================================================================
RELATIONSHIP REQUIREMENTS
======================================================================

Persist the normalized dependency concept:

predecessor activity -> relationship -> successor activity

Support at minimum:

- FS — Finish-to-Start.
- SS — Start-to-Start.
- FF — Finish-to-Finish.
- SF — Start-to-Finish.

Preserve lag when available.

Adapt the following conceptual structure to the existing architecture:

schedule_relationships
- id
- predecessor_activity_id
- successor_activity_id
- relationship_type
- lag
- created_at

Validation rules:

- Both referenced activities must exist.
- Relationship type must be supported.
- Self-referencing relationships must be rejected.
- Duplicate relationships must be handled safely and deterministically.
- Existing schedules without relationships must remain valid.
- Invalid references must produce understandable errors.
- Relationship information must remain available after export where the
  selected export format supports it.

Do not calculate delay ripple or critical path in Phase 4.

======================================================================
DATABASE REQUIREMENTS
======================================================================

Use the existing SQLAlchemy architecture.

If relationship persistence or external identifiers require schema
changes:

- Make the smallest safe schema change.
- Use the existing migration mechanism if available.
- If no migration mechanism exists, follow the current initialization
  approach and document it.
- Never reset the database during normal startup.
- Never destroy existing Phase 1-3 data.
- Test both a fresh database and an existing database.

======================================================================
PHASE 2 AND PHASE 3 INTEGRATION
======================================================================

Imported P6 activities must be usable by the existing Phase 2 matching
engine without rebuilding matching logic.

The expected flow is:

Imported activity
-> candidate retrieval
-> exact/identifier matching
-> fuzzy matching
-> semantic matching
-> temporal/context matching
-> ranked top matches

Phase 4 must reuse the existing Phase 3 workflow:

Top matches
-> confidence classification
-> automatic decision or planner review
-> approve, correct, reject, or create activity
-> audit trail
-> trusted final decision

Raw AI extraction must never directly update exported actual dates.
Only an approved or corrected Phase 3 final decision may supply trusted
actual_start or actual_finish values for export.

======================================================================
EXPORT REQUIREMENTS
======================================================================

Implement export from the internal ConSight schedule representation.

Where supported, export:

- Activity identifier.
- Activity code.
- Activity name.
- WBS.
- Discipline/category.
- Planned start.
- Planned finish.
- Approved actual start.
- Approved actual finish.
- External schedule identifier.
- External activity identifier.
- Predecessor activity.
- Successor activity.
- Relationship type.
- Lag.

Export safety rules:

- Export to a new file or explicit output path by default.
- Never silently overwrite the original imported file.
- Do not claim success if export failed.
- Report unsupported fields clearly.
- Document fields that cannot be preserved exactly.
- Preserve original external identifiers where possible.
- Do not export unapproved actual dates.

architecture.

- output format

VALIDATION REQUIREMENTS
======================================================================

Handle at minimum:

- Empty XER file.
- Malformed XER file.
- Unsupported file extension.
- Corrupted input.
- Missing activity identifier.
- Missing activity name when required by the existing model.
- Invalid planned start date.
- Invalid planned finish date.
- Finish before start.
- Duplicate activity identifiers.
- Invalid WBS reference where applicable.
- Invalid relationship reference.
- Unsupported relationship type.
- Self-referencing relationship.
- Duplicate relationship.

Errors must identify the relevant record, field, and reason whenever
possible.

Do not convert obviously invalid data into valid-looking data.
Preserve null where appropriate and report missing information.
