======================================================================
PROJECT PROBLEM STATEMENT
======================================================================

Project:
Intelligent Data Capture & Schedule-Linking Layer for Infrastructure
Project Management.

The system connects the structured planning side (L5/L6 infrastructure
schedule) with the unstructured execution side (field progress reports).

Phase 1 answers:
"What happened on site?"

Phase 2 answers:
"Which planned activity did that site event belong to?"

Phase 3 answers:
"Can we trust the match, and should it be automatically accepted or
reviewed by a planner?"

Phase 4 now answers:
"Can ConSight work with the real project schedule used by planners,
import it, preserve its important structure, connect field progress to
it, and export updated actuals back into the schedule workflow?"

3. IMPLEMENT XER / PRIMAVERA P6 IMPORT
------------------------------

Add a clean P6/XER import adapter.

The adapter should:

- accept a .xer file
- parse the relevant P6 schedule data
- identify activities
- extract activity codes/IDs
- extract activity names
- extract WBS information where available
- extract planned start
- extract planned finish
- extract discipline/category information when available
- extract relevant schedule metadata
- extract predecessor/successor relationships

- validate imported records
- report row/activity-level errors clearly

schedule analysis.

be replaced or extended later.

solution.

Do not add a large framework just for file parsing.

------------------------------
5. SCHEDULE RELATIONSHIPS
------------------------------

This is a critical Phase 4 requirement because Phase 7 will depend on
these relationships.

Support the schedule dependency concept:

predecessor -> relationship -> successor

At minimum, design support for:
- FS = Finish-to-Start
- SS = Start-to-Start
- FF = Finish-to-Finish
- SF = Start-to-Finish

Also preserve lag when available.

Use a normalized relationship representation, for example:

schedule_relationships
- id
- predecessor_activity_id
- successor_activity_id
- relationship_type
- lag
- created_at

Adapt this to the existing database architecture rather than blindly
copying the example.

Requirements:
- foreign keys must point to valid activities
- duplicate relationships should be handled safely
- invalid references should produce validation errors
- self-referencing relationships should be rejected unless there is a
  strong domain reason
- existing schedules without relationship data must continue to work

Do NOT implement Phase 7 delay-ripple calculations yet.

Only build and preserve the dependency data required for it.

8. ROUND-TRIP SAFETY
------------------------------

Round-trip means:

External schedule
-> import
-> normalized internal model
-> ConSight processing
-> export

The implementation should minimize information loss.

For fields that cannot be preserved exactly:
- identify them
- document them
- test the behavior

Never silently overwrite the original schedule file.

Export to a new file/path by default.

Use explicit naming or output handling.

If importing a schedule that already exists in the database, define safe
behavior for:
- duplicate import
- same external activity IDs
- updated schedule version
- changed planned dates
- removed activities

Do not invent complex version-control architecture.

For the SIH MVP, implement a simple deterministic and safe strategy.
