======================================================================

Turn accumulated CONSight project history into useful operational
insights.

Examples:

- Which activities consistently take longer than planned?
- Which work types repeatedly experience delays?
- Which disciplines show recurring execution patterns?
- What lessons were observed on similar activities?
- What productivity trends appear over time?
- What historical evidence is relevant to a planner reviewing a new

The goal is DECISION SUPPORT, not autonomous project management.

3. INSTITUTIONAL MEMORY PRINCIPLE
======================================================================

Institutional memory must be derived from stored project evidence.

Evidence sources may include:
- approved progress events
- planner corrections
- approved activity matches
- rejected matches, if useful and properly labeled
- actual vs planned dates
- delay impact results
- activity descriptions
- discipline
- WBS
- historical audit records

Do NOT use:
- unapproved speculative AI outputs
- fabricated lessons
- unsupported assumptions
- personal/private information unrelated to project operations

======================================================================
4. FACT / DERIVED / AI DISTINCTION
======================================================================

Every insight should be classifiable as:

FACT
A directly stored project record.

DERIVED
A deterministic metric calculated from project records.

AI SUMMARY
A language-model interpretation of facts/derived metrics.

Example:

FACT:
XX-101 actual finish = Sep 13.

DERIVED:
XX-101 finished 3 calendar days after baseline.

AI SUMMARY:
"XX-101 experienced a 3-day finish variance."

The AI summary must never introduce a new number or fact absent from the
structured evidence.

======================================================================
5. PRODUCTIVITY METRICS
======================================================================

Implement deterministic metrics appropriate to the available data.

Potential metrics:

Schedule adherence:
planned duration vs actual duration

Finish variance:
actual finish - planned finish

Start variance:
actual start - planned start

On-time completion rate:
completed activities meeting the chosen schedule criterion

Average delay:
mean delay among eligible activities

Median delay:
median delay

Discipline-level performance:
aggregated metrics by discipline

Activity-type performance:
aggregated metrics by normalized activity type/description where safely
available

Do not calculate metrics where required source data is missing.

Return:
- value
- sample size
- time range
- filters
- exclusions/limitations

Never present a metric without enough context.

======================================================================
6. PRODUCTIVITY NORMALIZATION
======================================================================

Be careful with activity names.

Examples:
"Concrete footing"
"Footing concreting"
"Foundation footing concrete"

These may refer to similar work, but the system must not blindly merge
them.

Reuse existing matching/normalization logic where appropriate.

If semantic grouping is introduced:
- make it explicit
- keep original activity identifiers
- store grouping evidence
- avoid destructive renaming

======================================================================
9. LESSON EXTRACTION
======================================================================

A lesson should only be created when supported by evidence.

Bad:
"Workers are usually slow in rainy weather."

No evidence → reject.

Good:
"Across 8 approved electrical cable-laying activities in the selected
period, 5 finished later than baseline."

This is a derived observation.

An AI-generated planner summary may then explain the pattern, but must
reference the underlying evidence.

======================================================================
10. NEMOTRON USAGE
======================================================================

Nemotron can be used for:

- summarizing historical evidence
- grouping semantically similar observations
- generating planner-readable explanations
- answering evidence-grounded natural-language questions
- synthesizing long historical context

Recommended architecture:

Structured project records
        ↓
Deterministic retrieval/filtering
        ↓
Evidence package
        ↓
Nemotron
        ↓
Structured/validated summary
        ↓
API response

Do NOT send the entire database blindly to the model.

Retrieve relevant evidence first.

Do NOT allow the model to:
- modify schedule activities
- modify progress events
- approve planner reviews
- change confidence scores
- change critical-path calculations
- create unsupported facts

======================================================================
11. EVIDENCE-GROUNDED AI
======================================================================

Every AI answer should receive a bounded evidence package.

Example:

Question:
"Why are piping activities taking longer?"

Evidence:
- 12 approved piping activities
- 7 had positive finish variance
- average variance = X
- median variance = Y
- date range = ...
- activity IDs = ...

Model instruction:
Answer only from the supplied evidence.
If evidence is insufficient, say so.
Do not invent causes.

The API should expose evidence references where practical.

======================================================================
12. NATURAL-LANGUAGE QUERYING

Pipeline:

→ deterministic database query
→ evidence package
→ optional Nemotron summary
→ response with evidence

Do NOT let the model generate arbitrary SQL.

filters against an explicit allowlist.
