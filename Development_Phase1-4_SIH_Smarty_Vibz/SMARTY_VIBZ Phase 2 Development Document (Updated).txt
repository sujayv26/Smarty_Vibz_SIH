Hybrid Schedule Matching Engine & Benchmark Evaluation
Reference basis: Phase 1 establishes schedule ingestion/storage, multi-format progress extraction (free text, Excel, Time Agent) and validated progress-event storage. Phase 2 extends that foundation rather than rebuilding it.

1. Phase 2 Objective
Build a lightweight, explainable Hybrid Schedule Matching Engine that consumes the structured Progress Events and Schedule Activities already produced and stored by Phase 1, identifies the most likely planned activities, ranks candidates, and returns the top three matches. Additionally, Phase 2 includes a benchmark dataset and accuracy evaluation framework that produces measurable metrics for judges.

Phase 1 answers: "What happened on site?"
Phase 2 answers: "Which planned activity did that site event belong to?" (with measured accuracy)

2. Direct Reference to Phase 1
Phase 1 defines the handoff boundary explicitly: schedule activities are stored from Excel, while free-text field reports, discipline-wise Excel progress, and Time Agent conversations are converted into validated Progress Events and stored in SQLite. Phase 1 also provides source_type (FREE_TEXT / EXCEL / AGENT_CHAT) on progress_events.

Phase 1 specifically provides the schedule_activity fields activity_code, activity_name, discipline, WBS and planned dates, and progress_event fields such as activity_reference, event_type, event_date, event_time, discipline, location, equipment_tag, raw_text, source_type and created_at.

7. Candidate Retrieval
For the Phase 2 MVP, candidate retrieval should remain simple and deterministic:
1. Equipment tag match
2. Discipline match
3. Keyword overlap
4. Full schedule fallback

The sample schedule is intentionally around 15–20 activities and contains similar activities for future matching, so a full-schedule fallback is acceptable and preferable to over-engineering.

8. Matching Components
8.1 Exact / Identifier Matching
Prioritize deterministic signals:
- Equipment tags
- Activity references/codes
- IDs and unique identifiers
- Strong domain keywords

Example: XX-101 in the Progress Event and XX-101 in the Schedule Activity should produce a strong exact signal.
This component must work completely offline.

8.2 Fuzzy Text Matching
Use RapidFuzz or an equivalent lightweight local library. It should handle word-order differences, minor spelling differences, abbreviations, similar phrases and singular/plural variations.

Progress:  "XX-101 spool erection"
Schedule:  "Erection of spool for XX-101"

8.3 Semantic Matching
Provide a SemanticMatcher abstraction so the semantic implementation can be replaced later.
Prefer a lightweight local embedding model if practical. The overall application must not depend on a live external LLM API. If the semantic component is unavailable, return a safe fallback using Exact + Fuzzy + Context.

8.4 Context and Temporal Matching
Discipline: Piping, Civil, Mechanical, Electrical, etc.
WBS: compare when present in both event context and schedule data.
Location: compare only when the event contains a location; never infer a missing location.
Equipment tag: compare as a strong contextual/identifier signal.
Event type: START/PROGRESS/COMPLETE/DELAY/HOLD can inform compatibility with activity wording/state.
Planned dates: compare event date with planned start/finish when dates are available.
Missing values are not mismatches by default; the corresponding signal should be treated as not applicable rather than guessed.

9. Hybrid Scoring Model
Formula:
Final Score =
    0.30 × Exact Score
  + 0.25 × Semantic Score
  + 0.20 × Fuzzy Score
  + 0.10 × Discipline Score
  + 0.10 × Context Score
  + 0.05 × Temporal Score

All component scores must be normalized to 0.0–1.0. These are MVP starting weights and may be tuned against the benchmark dataset.

10. Ranking and Match Confidence Behavior
After calculating the final score for each candidate:
Return Top 3, sorted descending.
Do not force an unrelated activity to become a match. If evidence is weak, return a low-confidence/no-strong-match indication while still preserving the ranked candidates where appropriate.

11. Explainable Results
Every returned candidate should include:
- Final score
- Individual score components
- Human-readable reasons

PIP-1023 — Erect Line 24"-XX-101
Final Score: 94%

Reasons:
✓ Equipment tag XX-101 matched
✓ Discipline Piping matched
✓ Activity wording is highly similar
✓ Location matched
✓ Schedule timing is compatible

Reasons must be generated deterministically from the component scores. Do not make a second LLM request just to generate explanations.

13.2 Benchmark Report Categories
Each report must have:
- input_text: the free-text or Excel-derived progress description
- expected_activity_code: the correct schedule activity code
- category: the type of test case
- source_type: FREE_TEXT or EXCEL or AGENT_CHAT

| FUZZY_WORDING | 10 | Same activity, different wording or word order |

| NO_MATCH | 5 | Reports that do not correspond to any schedule activity |

13.5 Accuracy Metrics Definitions
- Top-1 Accuracy: percentage of reports where the correct activity is ranked #1
- Top-3 Accuracy: percentage of reports where the correct activity appears in the top 3
- Precision at High-Confidence: percentage of auto-accepted matches (above threshold) that are correct
- Unmatched Rate: percentage of NO_MATCH reports correctly identified as having no strong match
- Average Processing Time: mean time from report input to matching result

13.6 Benchmark Test
The benchmark must be runnable as an automated test without internet access.
Test: test_benchmark_accuracy
This test loads the benchmark dataset, runs matching on each report, compares against ground truth, and asserts that metrics meet minimum thresholds:
- Top-1 accuracy >= 0.75
- Top-3 accuracy >= 0.85
- Precision at high confidence >= 0.90
- Unmatched rate detection >= 0.80

If thresholds are not met, the test should report the failing categories and specific reports, not silently pass.

The no-hallucination rule from Phase 1 continues into Phase 2: never invent missing activity IDs, equipment tags, locations, dates or disciplines.

|---|---|
| Invalid progress_event_id | Return 404 Not Found |
| Empty schedule | Controlled response; do not crash |
| Missing equipment tag | Use remaining signals |
| Missing discipline | Use remaining signals |
| Missing location | Do not guess; location signal not applicable |
| Missing optional fields | Do not crash; ignore unavailable signal |
| Ambiguous event | Return multiple ranked candidates |
| No relevant match | Return no-strong-match/low-confidence result |
| Semantic matcher unavailable | Fallback to Exact + Fuzzy + Context |
| Database failure | Controlled server error without sensitive internals |
| Two activities same equipment tag | Context + event_type matching must distinguish (e.g., erection vs. support vs. inspection) |
| Benchmark dataset missing | Return controlled error; do not crash |
