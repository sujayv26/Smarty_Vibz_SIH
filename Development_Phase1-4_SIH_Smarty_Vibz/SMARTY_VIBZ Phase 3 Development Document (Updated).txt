SMARTY_VIBZ | PHASE 3 DEVELOPMENT DOCUMENT (UPDATED)
Confidence Engine, Planner Review, New Activity Creation & Audit Trail

Project: Smarty_vibz
Problem Statement: Intelligent Data Capture & Schedule-Linking Layer for Infrastructure Project Management
Phase: Phase 3
Depends On: Phase 1 — FastAPI Backend Foundation, Multi-Format Extraction & Time Agent
Depends On: Phase 2 — Hybrid Schedule Matching Engine & Benchmark Evaluation
Primary Focus: Determine match reliability, provide planner decision workflow, and handle unmatched/new activities
Primary Output: Confidence classification, automatic matching or planner review, new activity creation, final decision and audit trail

1. PHASE 3 OBJECTIVE
Phase 1 answers: "What happened on site?"
Phase 2 answers: "Which planned activity did it belong to?" (with measured accuracy)
Phase 3 answers: "Can we trust the match? What if there is no match?"

Phase 3 consumes the ranked Top 3 schedule matches generated by Phase 2 and determines whether the best match is reliable enough to be automatically accepted.
If confidence is high, the system can automatically accept the best candidate.
If confidence is medium or low, the system should create a planner review item.
If no candidates match at all, the planner can create a new activity that was not in the original schedule (NEW).

The planner can then:
- Approve the suggested match
- Correct the suggested match (select a different existing activity)
- Reject the match (none of the candidates is appropriate)
- Create a new activity (for unmatched/new work not in the schedule) (NEW)
- Add an optional review note

Every final decision should be recorded in an audit trail.

3. PHASE 3 INPUT
The primary input is the result produced by Phase 2.
The system should use:
- progress_event_id
- Top 3 schedule candidates
- final scores
- score breakdown (exact, semantic, fuzzy, discipline, context, temporal)
- deterministic matching reasons
- Phase 2 benchmark accuracy data (to inform confidence threshold calibration)

Do not rebuild the Phase 2 matching engine.
Reuse its output.

4. CONFIDENCE ENGINE
The confidence engine should determine how trustworthy the best candidate is.
Confidence should consider:
- Best candidate final score
- Difference between first and second candidate
- Strength of exact identifier matches
- Fuzzy similarity
- Semantic similarity
- Discipline compatibility
- Context compatibility
- Temporal compatibility
- Missing information
- Ambiguity between candidates

The confidence calculation must be deterministic.
Do not call an LLM simply to calculate confidence.
Keep confidence thresholds configurable so that they can be tuned during testing.

Confidence thresholds should be calibrated using the Phase 2 benchmark dataset. For example, if the benchmark shows that matches above 0.85 have 95%+ precision, the HIGH threshold can be set to 0.85.

5. CONFIDENCE LEVELS
The MVP should support three levels.

HIGH CONFIDENCE
Strong evidence exists and the first candidate is clearly better than alternatives.
Action: HIGH → Automatic Match
The system selects the best schedule activity.

MEDIUM CONFIDENCE
The candidate is plausible but there is insufficient evidence for automatic acceptance.
Action: MEDIUM → Planner Review

LOW CONFIDENCE
Evidence is weak, ambiguous or the candidates are poorly separated.
Action: LOW → Planner Review

The system must never force an unrelated schedule activity to become a trusted match.

6. CONFIDENCE THRESHOLDS
Implement configurable thresholds.
For example:
HIGH: confidence >= configured high threshold
MEDIUM: confidence >= configured medium threshold and below high threshold
LOW: confidence < configured medium threshold

Store thresholds in configuration where practical.
Calibrate thresholds against the Phase 2 benchmark dataset so that:
- HIGH threshold achieves >= 90% precision (auto-accepted matches are correct 90%+ of the time)
- MEDIUM/LOW threshold catches most ambiguous cases

7. AUTOMATIC MATCHING
When the result is HIGH confidence:
- Select the highest-ranked candidate
- Store the selected schedule activity
- Mark the progress event as automatically matched
- Store confidence information
- Create an audit record
- Make the decision visible through the API

8. PLANNER REVIEW WORKFLOW
For MEDIUM or LOW confidence results, create a planner review item.
The review should contain:
- Progress event
- Raw field report
- Extracted event information
- Proposed schedule activity
- Confidence score
- Confidence level
- Top 3 candidates
- Score breakdown
- Matching reasons
- Review status
- Initial status: PENDING

9. PLANNER ACTIONS
The planner must be able to perform four actions.

9.1 APPROVE
The planner accepts the proposed activity.
PENDING → APPROVED
The proposed schedule activity becomes the final selected activity.

9.2 CORRECT
The planner selects a different schedule activity from the existing candidates or from the full schedule.
Example: AI Suggested PIP-1023, Planner selects PIP-1027.
The final selected activity should be PIP-1027.
The system must record that the planner corrected the original suggestion.

9.3 REJECT
The planner determines that none of the candidates is appropriate.
PENDING → REJECTED
The system must not force a schedule match.

9.4 CREATE NEW ACTIVITY (NEW)
When none of the candidates match, or when the progress event describes work not in the original schedule, the planner can create a new activity.
This directly addresses the problem statement's requirement to "flag unmatched/new activities for planner review rather than silently dropping them."

PENDING → NEW_ACTIVITY_CREATED

The planner provides:
- activity_code: a new code (e.g., UNPLANNED-001 or a code following the project's naming convention)
- activity_name: descriptive name for the new work
- discipline: the discipline of the work
- wbs: optional WBS path (may be null if unknown)
- planned_start: optional (may be null)
- planned_finish: optional (may be null)

The system:
1. Creates a new schedule_activity record with the provided details.
2. Marks the new activity as unplanned: is_unplanned = true (add this boolean field to the schedule_activities table or a separate unplanned_activities table).
3. Links the progress event to the newly created activity.
4. Records the decision as NEW_ACTIVITY_CREATED in the audit trail.
5. Makes the new activity visible in the schedule for future matching.

Example:
Progress Event: "Repainted the perimeter fence around the compound"
Phase 2: No strong match (all candidates below low threshold)
Phase 3: Confidence LOW, Planner Review created
Planner Action: CREATE NEW ACTIVITY
  - activity_code: MISC-9001
  - activity_name: Repaint perimeter fence
  - discipline: Civil
  - wbs: null
Planner Note: "This work was not in the original schedule. Creating as unplanned activity."
Audit Record: decision=NEW_ACTIVITY_CREATED, actor_type=PLANNER

10. REVIEW NOTES
Allow an optional planner note for all actions (approve, correct, reject, create new).
The note should be stored in the audit trail.

11. REVIEW STATUS
Recommended statuses:
- PENDING
- APPROVED
- CORRECTED
- REJECTED
- NEW_ACTIVITY_CREATED (NEW)

A completed review must not be modified accidentally.
If a review has already been completed, return an appropriate controlled error.

12. AUDIT TRAIL
Every automatic or planner decision should create an audit record.
The audit record should contain:
- progress_event_id
- proposed activity
- final selected activity (or null if rejected or new activity created)
- new_activity_id (if a new activity was created) (NEW)
- confidence score
- confidence level
- decision (AUTO_MATCH / APPROVED / CORRECTED / REJECTED / NEW_ACTIVITY_CREATED)
- reviewer note
- timestamp
- whether decision was automatic or planner-generated (actor_type: SYSTEM / PLANNER)

The purpose is to answer:
"Why did the system select this activity?"
"Who changed the original AI suggestion?"
"Was this activity auto-matched or planner-created?"

14. API SPECIFICATION
Implement APIs for the confidence and review workflow.

Evaluate Confidence
POST /confidence/evaluate/{progress_event_id}
Purpose: Retrieve Phase 2 matching result, calculate confidence, classify, automatically match HIGH confidence, create planner review for MEDIUM/LOW, return the result.

Pending Reviews
GET /reviews/pending
Returns all planner reviews waiting for action.

Review Details
GET /reviews/{review_id}
Returns complete review information.

Approve
POST /reviews/{review_id}/approve
Approves the proposed activity.

Correct
POST /reviews/{review_id}/correct
Allows the planner to select another valid schedule activity.

Reject
POST /reviews/{review_id}/reject
Rejects the suggested match.

Create New Activity (NEW)
POST /reviews/{review_id}/create-new
Allows the planner to create a new schedule activity that was not in the original plan.
Request body:
{
  "activity_code": "MISC-9001",
  "activity_name": "Repaint perimeter fence",
  "discipline": "Civil",
  "wbs": null,
  "planned_start": null,
  "planned_finish": null,
  "reviewer_note": "This work was not in the original schedule."
}
Response:
{
  "review_id": 5,
  "new_activity": {
    "id": 21,
    "activity_code": "MISC-9001",
    "activity_name": "Repaint perimeter fence",
    "discipline": "Civil",
    "wbs": null,
    "is_unplanned": true
  },
  "status": "NEW_ACTIVITY_CREATED",
  "audit_record_id": 12
}

Audit
GET /audit/{progress_event_id}
Returns the decision history for the progress event.
